## 1. Current state (inventory 2026-09-10; staging SQL run read-only)

**B-840.** Both `lite/bookings/page.tsx` and `executive/bookings/page.tsx` are 3-line shims over ONE component, `apps/ops-console/src/features/bookings/BookingsList.tsx`. The WHEN rail is a pure client-side filter: `bucketOf(iso)` (`:375-378`) = `utcDayDelta(pickup_time)` → `today | past | upcoming`; **`status` is never read**. A CANCELLED booking keeps its future `pickup_time` (there is no `cancelled_at` column; only `status` flips), so it lands in Upcoming, is counted in the chip (`:95-98`) and the header strip (`:239-243`), and is styled "IN 96 DAYS". The server (`/ops/bookings`, `OpsListQueryDto` `ops.dto.ts:104-125`) has no date parameter and orders by `created_at DESC` (`ops.service.ts:442`); the loaded window is 50 rows (`usePagedList`, PAGE 50 / MAX 500). The STATUS filter already offers "Cancelled" (`:34`, server-side), but it does not reset the WHEN bucket. Booking statuses: exactly ONE cancel state, `CANCELLED` (enum `lite_booking_status`; `status.test.ts:22-25/64-69` forbids inventing a pseudo-status). The console already knows the right notion of "committed future work" in two places — `executive/page.tsx:61-66` and `ops.service.ts:297-301` filter to `OPS_APPROVED/PAYMENT_PENDING/CONFIRMED/DISPATCHING` before the time window — and neither is reused here. **No test covers any of this** (no `bookingBuckets` / `bookingsQueue` test exists). Staging today: the ONLY booking with a future pickup is that cancelled one.

**B-841.** Every sidebar badge comes from one `GET /ops/dashboard` KPI row (`Shell.tsx:286`, `navBadges` `:297-304`, 5 s poll, no server cache). The Pro number is **`pro_pending + pro_requests`** (`Shell.tsx:301`): `pro_pending` = `pro_applications` in `PENDING_PROPOSAL/REVISION_REQUESTED` (`ops.service.ts:249-250`) and `pro_requests` = `COUNT(*) FROM pro_plan_missions WHERE status = 'REQUESTED'` (`:251`) — protection-date reservations awaiting officers, a different queue with its own page at **/pro/assignments** (`ProManagement.tsx:396, :428-465`, same predicate at `pro-management.service.ts:375-387`). The badge lands on the **Applications** item because `nav.tsx:129` carries `badgeKey: 'pro'` and the Assignments item (`:132`) carries none. Staging (SQL, read-only): `pro_pending 0`, `pro_requests 2` — the two rows are genuine (`REQUESTED` on two ACTIVE plans, dates 7–14 Sep and 16 Sep 2026). Latent: `pro_requests` has no join to the parent application's status and no date bound, and neither `cancel`/`opsCancel`/`reject`/`sweepExpired` cascades child missions, so a `REQUESTED` date on an expired plan or with long-past dates would be counted forever (none exist on staging today). Pins: `ops.service.projections.spec.ts:71-87` asserts the literal `FROM pro_plan_missions WHERE status = 'REQUESTED'`; `proApplicationsQueue.test.ts` pins `PRO_ACTIONABLE_STATUSES` and the page's `waiting` reduce; `nav.test.ts` pins that every nav item is a real page (a new route needs a nav entry — a local tab does not); `Shell.tsx:301` is unpinned.

## 2. Design decisions

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Why                                                                                                                                                                                                                                                            |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | **A fourth WHEN bucket, "Cancelled", in the same rail** (All dates / Today / Upcoming / Past / **Cancelled**). `bucketOf(status, pickupIso)`: `status === 'CANCELLED'` → `'cancelled'` regardless of date; otherwise the existing day-delta rule. Counts, the header strip and the `RelChip` ("IN 96 DAYS") follow the same function (a cancelled row shows "CANCELLED" instead of a countdown).                                                                                                    | "Just one separate tab" — the founder asked for a place, not a page. A WHEN bucket is one file, covers Lite and Executive at once, and needs no nav entry (`nav.test.ts`). COMPLETED stays in its date bucket (a completed job is past work; nothing to hide). |
| D2  | The pure rule moves to `apps/ops-console/src/lib/bookingBuckets.ts` (`WHEN_BUCKETS`, `bucketOf`, `bucketCounts`), dependency-free so the node project can pin it.                                                                                                                                                                                                                                                                                                                                   | The B-636/B-812 pattern: what a Jest project can reach gets a real test.                                                                                                                                                                                       |
| D3  | **No server change for B-840.** The WHEN window stays client-side over the loaded rows; that limitation is logged as **B-842** with the fix shape (a server `when` param + a count endpoint), not built here.                                                                                                                                                                                                                                                                                       | A new `listBookings` param breaks the placeholder pins in `ops.sections.spec.ts:79`; the founder's ask is the misfiled cancelled row, not the window.                                                                                                          |
| D4  | **Split the Pro badge.** `NavBadgeKey` gains `proRequests`; `nav.tsx`: Applications keeps `badgeKey: 'pro'` (= `pro_pending` only), Assignments gets `badgeKey: 'proRequests'` (= `pro_requests`); the SECURE PRO group badge stays the SUM of its items (both are ops work). `Shell.tsx:301` becomes two lines.                                                                                                                                                                                    | The item badge must mean the page's own queue; the group badge tells the operator something in the section needs them.                                                                                                                                         |
| D5  | **Harden `pro_requests` consistently in BOTH places**: the dashboard KPI (`ops.service.ts:251`) and the Assignments "Requests" queue (`pro-management.service.ts:375-387`) count `REQUESTED` missions **only on `pro_applications.status = 'ACTIVE'`**, i.e. `JOIN pro_applications pa … AND pa.status = 'ACTIVE'`. No date bound in this batch (a past-dated REQUESTED row on an active plan is still an ops decision to make). The projections pin is RE-POINTED to the new literal, not deleted. | Badge == queue, or the numbers disagree again (the B-593 class). The cascade-on-cancel is a follow-up (§9 Q2) — no orphan exists on staging today.                                                                                                             |
| D6  | Deploy: auth-service (D5) then ops-console (D1, D4). No APK, no mobile change.                                                                                                                                                                                                                                                                                                                                                                                                                      | Founder: push to main, no APK release.                                                                                                                                                                                                                         |

## 5. Edge cases (initial)

1. A CANCELLED booking whose pickup is today: `cancelled`, not `today` (status wins).
2. COMPLETED with a future pickup (data oddity): stays `upcoming` — unchanged, documented.
3. The Cancelled bucket + a STATUS chip other than Cancelled → empty set; the rail keeps the count so the user sees why.
4. The loaded window (B-842): "Cancelled 1" means "1 of the loaded rows"; the LOAD MORE label already says how many are loaded.
5. `pro_requests` after D5 on staging: still 2 (both plans ACTIVE) — the founder sees no number change on Assignments, only the placement.
6. The group badge when both items are 0: no badge (existing behaviour for 0).
