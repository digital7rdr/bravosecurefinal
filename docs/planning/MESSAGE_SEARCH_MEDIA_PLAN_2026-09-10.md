# Messenger + workspace search must find MEDIA (file names, captions) and show media rows

**Date:** 2026-09-10 · **Author:** Fable 5.1 (plan + critique) · **Makers:** Opus 5 · **Status:** PLAN v1 (critique loop in §8)
**Bug numbers reserved:** B-837 (search skips every media row — captions and file names), B-838 (search results are text-only — no media row, and a filename-only hit is dropped), B-839 (Files screen search sees only the last 200 rows per chat — logged, not fixed here)

---

## 0. The requirement (founder, 2026-09-10, same session)

> _"we can search messenger chat message and in workspace they search mess and now user should also be able to see the media also like if send a pdf or voice or picture with note user should see the docs also … now user only see mes now user should be able to search pdf name etc"_

| #   | Requirement                                                                                                                                                                                                              |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| R1  | Searching in the messenger (chat list and inside a chat) and in the workspace Channels box must also find **media messages**: a PDF/document by its **file name**, a **picture by its note (caption)**, videos likewise. |
| R2  | A media hit must **look like media** in the results (file icon / thumbnail + the file name), not a bare text line — "user should see the docs also".                                                                     |
| R3  | Voice notes: found where they can be. A voice note carries **no text** (no name, no caption), so it cannot match a typed query; the plan says what IS possible (§3 D6).                                                  |

## 1. Current state (inventory 2026-09-10 — file:line verified by the sweep agent)

**One SQL function serves all three boxes.** `MessengerHomeScreen.tsx:600-660` (chat list, lane 2), `ChatScreen.tsx:1878-1901` (in-chat sheet), `DepartmentChannelsScreen.tsx:449-485` (Channels, B-636) → `productionRuntime.searchMessages` (`:7049-7071`) → `SqlMessageStore.searchContent` (`sqlMessageStore.ts:552-593`):

```sql
SELECT * FROM messages
 WHERE conversation_id IN (…≤400)
   AND type = 'text'                                   -- drops EVERY media row
   AND content LIKE ? ESCAPE '\'                       -- only the body column
   AND (expires_at IS NULL OR expires_at > ?)
   AND (deleted_for_all IS NULL OR deleted_for_all = 0)
 ORDER BY created_at DESC, id DESC LIMIT ?
```

**Where the media text lives (`db.ts:168-264`, schema v22):**

| Thing                   | Row                                                                                                                                 | Searchable today | Why not                                                                                                                                                                                         |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Picture **with a note** | `type='image'`, **caption is `content`** (`ChatScreen.tsx:1444-1449`, B-707; send at `productionRuntime` sendMedia)                 | ❌               | only the `type = 'text'` predicate hides it — the cheapest win                                                                                                                                  |
| PDF / document **name** | `type='file'`, name in **`media_meta_json`** (`{name, sizeBytes, …}` — `types.ts:150-157`, written at `sqlMessageStore.ts:188/252`) | ❌               | never in the `WHERE`; and that JSON column also holds `thumbB64` (a base64 JPEG up to ~20 KB on image/video rows) — a naive `LIKE` over it scans megabytes and can false-positive inside base64 |
| Video                   | `type='video'`, name in `media_meta_json`, caption in `content`                                                                     | ❌               | same two blocks                                                                                                                                                                                 |
| Voice note              | `type='audio'`, `content=''`, `media_meta.name` absent (bubble renders the literal "Voice message", `ChatScreen.tsx:3617-3620`)     | ❌ and cannot be | there is no user text in the row to match                                                                                                                                                       |

**The hit pipeline drops media even if SQL returned it.** `channelMessageHits` (`channelMessageSearch.ts:134-157`) builds `buildSnippet(m.content ?? '', q)` and `continue`s on null — a PDF matched by name has an empty caption → dropped. `ChannelMessageHit` (`:71-76`) carries no `type` / `mime` / `media_meta`. `ChannelMessageHits.tsx:91` hard-codes a `#` icon; the in-chat sheet (`ChatScreen.tsx:2411-2437`) is a bare text snippet.

**Already in the repo and reusable:** `FilesScreen.tsx:124-129` `iconFor` (PDF/image/video/voice icon mapping) and `:79-98` `bucketFor`; `escapeLikeTerm` (`sqlMessageStore.ts:78-80`); the B-636 chunked read + `newestFirst` merge (`:60-67`, `:569-591`); `AttachmentFileViewer` name fallback (`:16-31`).

**Backup / schema facts that shape the design:** `media_meta` is ALREADY mirrored and restored (`backupWireV3.ts:137`), so reading `media_meta.name` needs zero backup work. `versionHash` is computed from the **serialiser**, not the table (`messageMirror.ts:628-643`), so **adding a column or an index to `messages` touches nothing — provided the column is NOT added to `serializeMessagePayload`** (`backupWireV3.ts:84-152`, stated three times there; adding it re-hashes every row → the B-94 `root_mismatch` class, I1). `db.ts` is a BACKUP_LOOP trigger file; `sqlMessageStore.ts`/`ChatScreen.tsx`/`MessengerHomeScreen.tsx` are MESSAGE_LOOP trigger files. `searchContent` takes no lock and opens no txn (M14) — keep it so. The tombstone applier already blanks `content` AND `media_meta` (`messageMutationApply.ts:100-107`), so a deleted-for-all PDF cannot resurface by name.

**Test debt found:** the chat-list search (A1, the two-lane union at `MessengerHomeScreen.tsx:667-674`) and the in-chat sheet (A2) have **no test at all**. `sqlMessageStoreEngine.test.ts:377` pins the current wrong behaviour ("searches TEXT rows only — a media caption is not a body"). `logAudit.test.ts` bans `.content`/`plaintext`/keys but has **no pattern for a file name** — a `console.warn(meta.name)` would ship green.

**B-839 (logged, deferred):** `FilesScreen.tsx:473-482` searches file names in JS over `selectMediaMessages`, i.e. the in-memory window of the last 200 messages per conversation (`messengerStore.ts:519`) — old files are invisible there. Different screen from the three boxes in R1; noted at `FilesScreen.tsx:441-447`. Not fixed in this batch (§9 Q2).

## 3. Design decisions

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Why                                                                                                                                                                                                                                                                                                                                                                      |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D1  | **Add a derived, nullable `media_name TEXT` column to `messages` (schema v23)**, populated in `doUpsert` from `msg.media_meta?.name` (trimmed, ≤255), backfilled ONCE in the v23 migration with `UPDATE messages SET media_name = json_extract(media_meta_json, '$.name') WHERE media_meta_json IS NOT NULL AND type IN ('file','image','video','audio')`. **NOT added to `serializeMessagePayload`.**                                                                                                                         | A per-keystroke `LIKE` over `media_meta_json` would scan every image's base64 thumbnail and can false-positive inside base64; `json_extract` at query time parses those bytes on every search. ## 6. Edge cases (initial — the edge-case agent extends)

1. A query that appears only inside a thumbnail's base64 must not match (D1 makes the column the only name source; pinned).
2. Name with `%`/`_`/`\` (e.g. `Q3_report_100%.pdf`) — `escapeLikeTerm` applies to the same bound pattern; pinned.
3. Case: SQLite `LIKE` is ASCII-case-insensitive only; a non-ASCII file name matches exactly as today's bodies do (documented, not changed).
4. A media row that is BOTH matched by caption and by name: one hit, `matchedOn: 'body'`, title = name.
5. Tombstone: `deleted_for_all` rows are excluded by the predicate AND their `content`/`media_meta` are blanked — `media_name` must ALSO be blanked by the tombstone applier's upsert (it goes through `doUpsert` with `media_meta: null` → NULL). Pin it.
6. Disappearing messages: `expires_at` predicate unchanged.
7. Album-grouped photos: each photo is its own row → each caption hit is its own result; the album grid is unaffected.
8. Forwarded media keeps its `media_meta.name` → findable in the destination chat.
9. A 2-char floor stays; a 1-char query never hits SQL.
10. Very large photo threads: the search touches only `content`/`media_name` — no JSON parse per keystroke.
11. Downgrade (1.0.306 → 1.0.305): the extra column is ignored by the older `SELECT *`→`rowToMessage`; the older `doUpsert` INSERT names its columns, so no failure.
12. Voice notes: D6.
