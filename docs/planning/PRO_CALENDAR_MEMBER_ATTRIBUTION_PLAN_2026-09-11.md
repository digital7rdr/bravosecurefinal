# Pro coverage calendar — the root sees every linked member's dates, labelled; a member sees only their own

**Date:** 2026-09-11 · **Author:** Fable 5.1 (plan + review) · **Makers:** Opus 5 · **Status:** PLAN v1
**Bug numbers reserved:** B-852 (the coverage calendar shows every rider's protection dates to every rider, unattributed — the root cannot tell whose dates they are and members see each other's), B-853 (Bravo GeoRisk heat map removed — founder decision, tracked in the same build)
**Founder decision (2026-09-11, asked):** _"Root sees all, labelled; members see own."_ Same-build item: _"Remove the heat map from Bravo GeoRisk."_

## 1. Current state (verified 2026-09-11)

- `pro_plan_missions(application_id, requested_by, mission_dates, status, …)`. A member riding a root's plan (`getMine` ride-along, B-843 A12) requests dates on the ROOT's application (`requestMission` → `assertPlanAccess` accepts an active, non-held member, `pro-applications.service.ts:489-503`).
- `listMissions(userId, id)` (`:687-695`) returns EVERY mission on the application to anyone who passes `assertPlanAccess` — the root and every member. `MISSION_COLS` (`:121-124`) projects `requested_by` but no name.
- `SecureProCalendarScreen.tsx` paints all missions (`paintedDateStatus`, `missionsByDate`), lists them under REQUESTS (`:434-470`) and in the day/row sheet (`:588-640`) with "Your note" for every note; nothing shows who requested. RELEASE (`cancelMission`, `:579-600`) is offered on every row and the server lets ANY plan member cancel ANY mission on the plan (`SELECT … WHERE id = $1 AND application_id = $2`, no requester check).
- Staging: 25 missions, 2 requested by a member (Jack on Baine Kriel's plan, both COMPLETED).

## 2. Design

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Why                                                                                                        |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| D1  | **Server scopes by caller.** `listMissions`: the HOLDER (`userId === app.user_id`) gets every mission; a member gets `AND requested_by = $2` only. Every row carries `requested_by_name` (`LEFT JOIN public.users ru ON ru.id = pm.requested_by`, `ru.display_name`); a NULL `requested_by` (legacy) is treated as the holder's.                                                                                                                                                                                                                                                | The founder's rule is a data-access rule, so it lives on the server; the client cannot be trusted to hide. |
| D2  | **Cancel follows the same rule.** `cancelMission`: the holder may release any mission on the plan; a member only one they requested (`AND (requested_by = $3 OR $4)` where `$4` = is-holder) — else 403 `not_your_mission`.                                                                                                                                                                                                                                                                                                                                                     | A member could release another member's (or the root's) dates today.                                       |
| D3  | **Client attribution.** `ProPlanMission.requested_by_name?: string \| null`. Pure helpers in `calendarMissions.ts`: `requesterOf(mi, selfId)` → `'self'` or the display name; `requesterChips(missions, selfId)` → `[All, You, <name>…]` only when ≥ 2 distinct requesters; `filterByRequester(missions, key)`. The calendar's REQUESTS rows and the day/row sheet show **"Booked by {name}"** for a mission not requested by the viewer; "Your note" becomes "Note" for those. Paint tones stay STATUS tones (attribution is text, never colour — the B-821 legend is status). | The root reads the calendar as a plan overview; the name is the missing fact.                              |
| D4  | **Filter chips** (holder view only, when ≥ 2 requesters): a horizontal chip row above the calendar — All · You · one per member — filtering paint, BOOKED DAYS month chips, REQUESTS and sheets together (one `visibleMissions` memo). Default All. Not persisted.                                                                                                                                                                                                                                                                                                              | The founder asked for a filter per person.                                                                 |
| D5  | **RELEASE button** shown only when the viewer may cancel (holder, or own mission); the server refuses the rest anyway (D2).                                                                                                                                                                                                                                                                                                                                                                                                                                                     | UI must not offer an action the server refuses.                                                            |
| D6  | **Unchanged:** the ops console mission queue; `requestMission`; `getMine` ride-along; the calendar legend; B-821 paint precedence; `SecureProMissionsScreen` (the sibling list) gets the SAME "Booked by" row line via the shared helper but no chips.                                                                                                                                                                                                                                                                                                                          | Minimal; one helper for the label (duplicate-copy class).                                                  |

## 4. Edge cases

1. Multi-root member (B-843): rides the OLDEST active plan; their calendar shows that plan's own requests only. Fine.
2. A member revoked AFTER requesting: their missions stay on the plan (ops may still have assigned a team); the root still sees them labelled; the ex-member no longer passes `assertPlanAccess` (404/403 as today).
3. `requested_by` NULL on legacy rows → holder's (D1); name → the holder's display name.
4. Two members with the same display name → chips keyed by user id, labels disambiguated with the id tail only on collision (reuse `orgDisambiguation.collidingOrgNames`).
5. The holder's own requests → chip "You", no "Booked by" line.
6. Old APK vs new server: a member's calendar simply shows fewer rows (own only) — no error; `requested_by_name` ignored. New APK vs old server: no name → helper falls back to "a member" and no chips (chips need ≥ 2 distinct requesters, which the old server still delivers — then the label reads "Booked by a member"). Server first.
7. Ops decide notifications: check whom `pro-management` notifies on decide (holder vs requester) — report, do not change unless it is the holder only, in which case add the requester as a second recipient (P1, small) — **maker reports; Fable decides.**
