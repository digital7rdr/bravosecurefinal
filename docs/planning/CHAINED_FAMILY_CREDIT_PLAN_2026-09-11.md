## 0. The requirement (founder, 2026-09-11)

> _"On link member: suppose A adds B as a linked member; now B can also add members C and eventually uses A's credit. It's good but the root member A must know that C member uses [it]."_ Asked which behaviour — answer: **"Chained credit through B"**: C's bookings may be paid from A's wallet inside B's allowance, with A seeing C's usage line by line.

| #   | Requirement                                                                                                                                                                                           |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | A linked member B (member of root A) who holds their own members C can have C's bookings paid from **A's wallet**, counted against **B's allowance** on A's plan (and against C's own limit under B). |
| R2  | A sees every such charge attributed to C ("C via B"), on the app's member sheet and the ops console, and A's existing 80/90/100 % warnings for B's allowance include C's spending.                    |
| R3  | A's exposure never exceeds what A already granted B (B's limit); A can stop the chain; B's own wallet stays the default (today's behaviour) until the chain is switched on.                           |

## 1. Current state (verified 2026-09-11 — inventory in the session log)

- **One hop, by construction.** `resolvePayer(userId, chosen)` (`family.service.ts:690-762`) returns the member's OWN row: `payerId = row.holder_id`, `familyRowId = row.id`. The escrow charge (`dispatch.service.ts:1659-1683`) re-resolves `WHERE fm.member_id = $1 [client] AND fm.holder_id = $2 [payer_user_id] … FOR UPDATE OF fm`, debits the payer's `wallet_balances` (`wallet.service.ts:596-622`, `actor_user_id = member`, `metadata.family_row_id`), bumps `spent_credits WHERE id = $1`, returns `familyRowId` for `notifyUsageThreshold`. `payWithCredits` (`booking.service.ts:1220-1449`) mirrors it. Refunds (`wallet.service.ts:673-702`) reverse by `metadata->>'family_row_id'`, fallback `(member, holder)`.
- **B → C is allowed today** (`invite()` checks nothing about the inviter being someone's member), and C's charges land on **B's wallet** — nothing reaches A. A credit-request approval raises B's `spend_limit_credits`; it moves no credits (`family-quota.service.ts:322-360`).
- **A's member-spend view keys on the ledger actor**: `memberSpend(holderId, rowId)` (`family.service.ts:849-910`) `WHERE user_id = $1 AND actor_user_id = $2` — a C-originated charge (`actor_user_id = C`) would be invisible on B's line. The console's `familyMemberSpend` API has NO UI caller (`apps/ops-console/src/lib/api.ts:2881`).
- **Staging:** 0 members who are also holders today.

## 2. Design decisions

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Why                                                                                                                                                                                  |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D1  | **The chain is a switch on B's membership row under A** — `family_members.funds_sub_members BOOLEAN NOT NULL DEFAULT false` on the `(holder = A, member = B)` row, plus a partial unique index `ON family_members(member_id) WHERE funds_sub_members AND status IN ('pending','active')` so a member funds their own members from at most ONE root. Default OFF = today.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | R3: opt-in, bounded by B's limit, one funding root even when B has several (B-843).                                                                                                  |
| D2  | **Who may flip it:** B (on their membership: "Fund my members from A's allowance") and A (on B's row: "B's members may spend this allowance"); ops on the console. Every flip is a `family_quota_audit` row (`action = 'fund_members_on' / 'fund_members_off'`, actor in `metadata`) and a push to the OTHER party (`familyFundingChanged(userId, familyRowId, enabled)` — ids + boolean only). Turning it on when another root already funds B's members → 409 `funding_source_already_set`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | R2/R3: A must know; A can stop it; B controls their own roots.                                                                                                                       |
| D3  | **Resolution (create time), ONE extra hop.** C chooses payer B (existing selector). `resolvePayer(C, B)` finds the `(B, C)` row as today; NEW: it then looks for B's funding row `(A, B)` with `funds_sub_members`, `status = 'active'`, not held, A not suspended. If found: `payerId = A` (the WALLET), `familyRowId = (B,C).id`, `fundingRowId = (A,B).id`, `holderId = B`, `fundingHolderId = A`. If not found (off, held, revoked, suspended): plain one hop to B's wallet — exactly today. The booking stamps `payer_user_id = A` AND a new `lite_bookings.payer_via_user_id = B` (NULL for every non-chained booking). Exactly one hop: if A is itself funded by Z, C's booking never climbs to Z.                                                                                                                                                                                                                                                                                                                                                                                                                  | `payer_user_id` keeps meaning "the wallet that pays" for every existing reader (refunds `creditTo`, ops "paid by", history); the via column carries the chain. One hop kills cycles. |
| D4  | **Charge time (escrow + legacy pay), fail-closed.** When `payer_via_user_id` is set: lock the UPSTREAM row `(A, B)` first, then the member row `(B, C)`, then A's wallet (MON-4 order: family rows before the wallet row; upstream-before-member is the canonical order for every chained charge so two concurrent charges cannot deadlock). Checks: `(B,C)` active/not held/C's cap; `(A,B)` active/not held/`funds_sub_members`/B's cap (`spent + credits <= limit`)/A not suspended. Any failure → `charge_failed_family` (escrow) / the existing coded refusals (legacy pay), never a silent switch to B's wallet after the stamp (B-384). Debit A's wallet; bump `spent_credits` on BOTH rows; ledger row `user_id = A`, `actor_user_id = C`, `metadata = {family_row_id: (A,B).id, via_family_row_id: (B,C).id, via_user_id: B}`; return both row ids; post-commit `notifyUsageThreshold` for BOTH rows (A hears about B's allowance, B hears about C's limit). **The existing B-384 block in `dispatch.service.ts` stays byte-identical**; the chained branch is a separate block guarded by `b.payer_via_user_id`. | R1/R3 with the same discipline as B-384.                                                                                                                                             |
| D5  | **Refunds** reverse BOTH rows: `reverseFamilySpend` reads `family_row_id` and `via_family_row_id` from the ledger row; the `(member, holder)` fallback is one-hop only and must not be reached for a chained charge (metadata is always written). Re-arm bands on both rows.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Money symmetry.                                                                                                                                                                      |
| D6  | **A's visibility.** `memberSpend(A, rowB)` and `usage(A)` key on the LEDGER ROW ID, not the actor: `WHERE user_id = $1 AND (metadata->>'family_row_id' = $rowB OR actor_user_id = $memberB)`, projecting `actor_user_id` + the actor's display name and `via_user_id`; A's member sheet lists "C via B · booking · 258 BC"; the console `LinkedMembersCard` finally wires `familyMemberSpend` (a "Spending" disclosure per member) and shows a "Funds their members" column + toggle. The app's holder roster row shows "also holds N members · funded from your allowance" when the switch is on. History rows (`bookingHistoryRows.ts`, `booking-history.service.ts payer_name`): "Paid by A via B" for the member C; B's own history untouched.                                                                                                                                                                                                                                                                                                                                                                         | R2.                                                                                                                                                                                  |
| D7  | **C's view (LM-B7).** C sees B as the payer with `effectiveSpendable = min(C's remaining under B, B's spendable)`, where B's spendable is B's remaining allowance on A capped by A's wallet when chained, else B's wallet — computed server-side in `myMemberships()`; C never sees A's name, balance or limit. Refusals to C name B (`holder_id = B`); `familyChargeBlocked` goes to C, B and A (A is the wallet).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | The member sees their own root only.                                                                                                                                                 |
| D8  | **Old clients / old server.** Old APK as C: nothing changes (the chain is server-side; C's selector shows B). Old APK as B or A: cannot flip the switch (new endpoints) — default OFF, so nothing changes. New APK on an old server: the toggle endpoint 404s → hidden. Migration → server → APK → console (HARD).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Additive everywhere.                                                                                                                                                                 |
| D9  | **Unchanged on purpose:** credit requests (C asks B; B asks A — each on its own row); holds/revokes (a held or revoked `(A,B)` row simply breaks the chain at charge time, fail-closed, and at create time falls back to B's wallet — the stamp decides which); the Pro ride-along; the family location row.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Scope.                                                                                                                                                                               |

## 5. Edge cases (initial — the edge-case agent extends)

1. B has roots A and Z, both willing: only one may fund (D1 unique) — B picks; A's toggle on B's row fails 409 while Z funds.
2. A holds B → chain dead at charge time (fail-closed) and at create time (fallback to B's wallet, stamp = B). A revokes B → same; the switch on a revoked row is inert.
3. A suspended → chained bookings refused with `ROOT_ACCOUNT_SUSPENDED` naming B? No — naming B leaks nothing; C hears "B's account can't pay right now"; B and A get `familyChargeBlocked`.
4. C's own limit under B (C's cap) and B's cap under A both apply; the tighter wins; refusal codes stay the existing ones with `holder_id = B`.
5. Cycle A↔B: A funds B's members, B funds A's members: C (under B) → A's wallet; D (under A) → B's wallet; one hop each; no recursion.
6. Refund after the switch is turned OFF: the ledger metadata still names both rows → both reversed.
7. Refund after B was REVOKED by A: `(A,B)` row still exists (revoked) → `spent_credits` decrement on a revoked row is harmless.
8. `memberSpend` for A over B when B's members are many: pagination unchanged (LIMIT); actor names via one LEFT JOIN.
9. Concurrency: two of B's members charging at once → both lock `(A,B)` first → serialised; B's cap enforced under lock.
10. A's 80/90/100 % warnings: `notifyUsageThreshold((A,B).id)` fires for C's charges too — the push says "B's allowance" (existing copy) — fine; B's own warning for C's limit fires separately.
11. Legacy pay with a stale stamp (`payer_via_user_id` set, switch since turned off): refused at charge time (fail-closed) — the client offers "pay from another account" (B-843 A7 flow) → C picks B again → re-resolves without the chain → B's wallet. Pin.
12. Ops "test dispatch" bookings: no `payer_via_user_id` → untouched.
