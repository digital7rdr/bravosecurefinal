## 0. The requirement (founder, 2026-09-10)

> _"one person can be added as member in org also as individual, and there is no limit — one user can be a member under multiple root accounts, in an org too. So when he books he should have the option of which root account he wants to use. You handle that part and the edge cases also."_

| #   | Requirement                                                                                                                                                                                           |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | A person may be an active member under ANY number of root accounts at once (their family, their employer, several companies). No limit.                                                               |
| R2  | When that person books, they choose which root pays (or their own wallet). The charge, the quota bookkeeping and any refund follow THAT root.                                                         |
| R3  | Every place that today assumes "the member's one root" (quota card, credit requests, Pro plan ride-along, warnings, location sharing) must behave sensibly with several — and the edge cases handled. |

This overrules plan Q1 of `PRO_MEMBERS_UNLIMITED_PLAN_2026-09-10.md` (which kept ONE membership by default).

## 1. Current state (verified 2026-09-10)

**The one-root rule lives in four places.** DB: unique index `family_members_one_active_per_member ON family_members(member_id) WHERE status = 'active'` (`20260602000000_family.sql:24-25`). Server: `invite()` refuses `member_in_another_family` (`family.service.ts` ~`:110-114`), `accept()` refuses `already_in_a_family` (~`:233-239`), and the console batch surfaces the same code. Mobile copy: "They are already a member of another account."

**The money path already carries the payer — per booking.** `lite_bookings.payer_user_id` is stamped at request time by `requestAuto` (LM-B7, `booking.service.ts:797-830`, insert at `:902`) via `FamilyService.resolvePayer(clientId)` (`family.service.ts` ~`:412-445`, returns ONE holder), and the escrow charge (`dispatch.service.ts:1628-1674`, B-384) re-resolves **by `(member_id = client, holder_id = payer_user_id)`** under `FOR UPDATE OF fm` at charge time; its spent bump (`:1706`) and the refund reversal (`wallet.service.ts:673-701`, row-keyed via `metadata->>'family_row_id'`, fallback `(member, holder)`) key the same way. So **with a unique `(holder_id, member_id)` open row, the whole escrow lane is already multi-root-safe** — the payer identity IS the root's user id. The legacy `payWithCredits` path (`:1134`) still calls `resolvePayer(clientId)` at charge time with no holder — that is the one charge site that must learn the choice. The pre-flight soft check (`:807`) likewise.

**Member-side reads that return ONE row by `member_id`:** `myMembership()` (~`:342-405`, → `FamilyQuotaCard`), `requestCredit(userId, …)` (`family-quota.service.ts:206-217` — "resolves the membership from user.sub"), `notifyUsageThresholdForMember(memberUserId)` (`:468-471`, called from the escrow accept which KNOWS `b.payer_user_id`), the Pro ride-along (`pro-applications.service.ts:298-312` — "rides the OWNER's ACTIVE plan": `qOne` picks an arbitrary holder with N rows), `reportLocation` eligibility (`qOne` — any active non-held membership; fine). Holder-side reads are per holder already; the console `member_of` is already an array.

**Client:** the booking body (`BookingCreateBody` → `POST /bookings/request-auto` / `POST /bookings`) has no payer field; `CreditPaywallScreen` calls `payWithCredits(id)` with no body; the profile shows one `FamilyQuotaCard`; `humanCreditMessage` knows `family_spend_limit_exceeded` / `root_account_suspended` only.

## 2. Design decisions

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | Why                                                                                                                                                                                                                                                                                                                    |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | **Migration `20260910230000_family_multi_membership.sql`:** `DROP INDEX family_members_one_active_per_member`; `CREATE UNIQUE INDEX family_members_holder_member_open ON public.family_members(holder_id, member_id) WHERE member_id IS NOT NULL AND status IN ('pending','active')`. The holder+phone pending index stays.                                                                                                                                                                                                                                                                                                                                                                                                          | The ONLY invariant that must survive is "one open row per (root, member)" — it is what makes `(member, holder)` a key for the charge-time re-resolve, the spent bump and the refund fallback. An index, not a check-then-insert (the B-709 §12 lesson); `invite`'s `ON CONFLICT DO NOTHING` already swallows the race. |
| D2  | **Payer = `payer_user_id`, chosen at booking CREATION.** `CreateBookingDto` gains `payer_user_id?: string` (UUID, optional). `resolvePayer(userId, chosenHolderId?)`: `chosen === userId` → self; `chosen` set → the ACTIVE, non-held membership under that holder or `400 {code:'PAYER_NOT_ELIGIBLE', message:'payer_not_eligible'}`; `chosen` absent → 0 memberships → self, exactly 1 → that (today's behaviour), ≥2 → `400 {code:'PAYER_CHOICE_REQUIRED', message:'payer_choice_required', options:[{holderId, holderName, spendLimit, spent, remaining, held}]}`. Both request paths (auto + legacy create) stamp `payer_user_id` at insert.                                                                                    | The escrow lane already reads the stamped payer and re-validates the `(member, holder)` row under lock at charge time (B-384) — no new column, no new lock order. An explicit refusal beats a silent charge to the wrong root: for money, a surprise is the worse failure.                                             |
| D3  | **`payWithCredits` (legacy path) uses the booking's stamped `payer_user_id`**, re-validated at charge time the B-384 way (`(member, holder)` row `FOR UPDATE`, hold/suspension/cap), and accepts `payerUserId?` in its body for bookings created before the stamp existed (falls back to `resolvePayer(client, body.payerUserId)`).                                                                                                                                                                                                                                                                                                                                                                                                  | One rule for both charge sites: the payer is decided once, at creation, and every debit re-checks the SAME membership row. `resolvePayer(client)` with no holder at charge time would pick an arbitrary row once N exist.                                                                                              |
| D4  | **Member-side reads become per-root.** `GET /family/memberships` → all active/pending memberships (`myMemberships()`); `GET /family/membership` (old clients) → the OLDEST active one (deterministic: `accepted_at ASC`). `POST /family/credit-requests` takes `holderId?` — required (`400 HOLDER_REQUIRED` + options) when the member has ≥2 memberships. `notifyUsageThresholdForMember(memberUserId, holderUserId)` — the escrow caller passes `b.payer_user_id`. The Pro ride-along picks the OLDEST membership whose holder has an ACTIVE plan (`ORDER BY fm.accepted_at ASC`), so `via_owner` is deterministic.                                                                                                               | Every "which root?" question has a deterministic answer or an explicit choice; nothing is `qOne` over an ambiguous set any more.                                                                                                                                                                                       |
| D5  | **Mobile: a "Pay from" selector in the booking flow** (the step that commits to Bravo Credits) — rows: "My wallet · {balance} BC" + one per active membership "{holderName} · {remaining} left" / "no limit" / "on hold" (disabled); default: the only membership when there is exactly one (today's behaviour), "My wallet" when none, **no preselection when ≥2** (Continue disabled until chosen). The choice rides `payer_user_id` in the create body. `CreditPaywallScreen` (legacy pay) reuses the same selector and sends `payerUserId`. `humanCreditMessage` learns `payer_choice_required` ("Choose which account pays for this booking.") and `payer_not_eligible` ("That account can't pay for this booking right now."). | R2 verbatim. Old-server tolerant: if `memberships` 404s, fall back to `membership()` (one card).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | R3.                                                                                                                                                                                                                                                                                                                    |

## 5. Edge cases (initial — the edge-case agent extends)

1. The chosen root revokes/holds the member, or lowers the cap, between request and accept: the B-384 charge-time re-resolve on `(member, holder)` fails the charge neutrally (`charge_failed_family`), both parties are woken — unchanged, now per root.
2. Refund of a booking paid by root A while the member is also in root B: `reverseFamilySpend` prefers the charge-time `family_row_id` and falls back to `(member, holder = A)` — never touches B.
3. A member who is ALSO a holder: options = self + memberships; a root's own bookings are theirs (no implicit chain).
4. Two roots both with ACTIVE Pro plans: dashboard access via the oldest such membership; `via_owner` names that holder; the booking's payer is still whichever the member chose.
5. Same person invited by root A and root B while both pending: both accepts succeed (no cross-root refusal); two pending rows from the SAME root are still refused (index).
6. The console batch adds the same phone under two different roots: both `ok`.
7. Old APK + ≥2 memberships: booking fails with `payer_choice_required` until the app is updated (D8).
8. A held membership is listed in the selector but disabled ("on hold"); a revoked one is not listed.
9. `spent_credits` / warnings / credit requests are per membership row — a member can be at 100% with root A and 0% with root B.
10. Location: one row, read by every active root (D7).
11. The member's own wallet stays selectable even when they have memberships (a member may prefer to pay themselves).
12. `payer_user_id` chosen = a root the member is NOT under → `PAYER_NOT_ELIGIBLE`, never a silent fallback to self.
