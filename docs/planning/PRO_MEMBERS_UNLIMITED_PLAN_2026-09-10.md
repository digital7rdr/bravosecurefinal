### 1.6 Invariants that must survive (do not "fix" these)

- **One ACTIVE membership per user** — unique index `family_members_one_active_per_member`; `invite` → `member_in_another_family`, `accept` → `already_in_a_family`. `resolvePayer` depends on it (exactly one payer). Multi-membership is a founder question (§9 Q1), not in scope.
- **Invitee must already hold an individual Bravo account** (founder rule 2026-08-03, `family.service.ts:82-99`). Pending-by-phone rows are not created (the read side still tolerates them via `linkPendingInvitesByPhone`).
- **Holder-scoped endpoints** — every `/family/*` route derives the holder from `user.sub`; no body carries a holder id. The new ops routes are the ONLY place a holder id comes from a path, and they sit behind `AdminGuard` + `RequireRoles('SUPERVISOR','ADMIN')` + CSRF + audit.
- **MON-4 lock order** and the atomic charge in `booking.service.ts` / `dispatch.service.ts` — untouched.
- **B-709 §19 floor** (`QUOTA_BELOW_SPENT`) applies to ops-set limits too, because the ops route calls the same `FamilyQuotaService.setQuota`.

## 3. Design decisions

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                        | Why                                                                                                                                                                                                                            |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D1  | **Delete the cap outright** (no configurable per-root limit, no ops "seat" concept). Keep `POST /family/request-seats` as a **legacy shim**: returns `{ok:true}`, emits an ops-feed row "legacy client requested seats — cap removed in 1.0.305, advise update". Remove `familyApi.requestSeats` from the new client.                                                                                                                           | A 1.0.304 APK at 4 active members computes `atCap` client-side and shows only the request CTA; the shim keeps that button honest until they update. YAGNI on a configurable cap — nobody asked for one.                        |
| D2  | **Relationship: stop collecting, stop returning, keep the column.** DTO keeps `relationship?` (accepted, ignored) so old APKs pass validation; INSERT writes NULL; every SELECT/DTO/type drops the field. No migration.                                                                                                                                                                                                                         | Old APK reads `m.relationship` → `undefined` → no badge. Column drop is a later cleanup migration (§9 Q4).                                                                                                                     |
| D3  | **Member naming = the person's display name** (or phone while pending). No "Member 1/2" numbering, no type badge.                                                                                                                                                                                                                                                                                                                               | The chat's "member 1, member 2" was an example of neutrality, not a numbering scheme; the list already shows names.                                                                                                            |
| D4  | **List paging is offset-based, server-side search on name/phone, default page 100, max 200; response keeps `members` and adds `total` + `counts {active, pending, held}`.**                                                                                                                                                                                                                                                                     | Offset paging is enough at thousands per holder (indexed on `holder_id,status`); a cursor is more code for no measured need. Keeping `members` is old-APK compat.                                                              |
| D5  | **`usage()` returns the top 50 members by spend; `totalSpent` is a SQL SUM over ALL active members.**                                                                                                                                                                                                                                                                                                                                           | The usage view is a bar chart; 4,000 bars is not a feature.                                                                                                                                                                    |
| D6  | **Console ops routes are thin wrappers over the existing holder-scoped service methods**, with `holderId = :id` from the path, `actorId = req.admin.user_id`, `actor_role = 'ADMIN'` on the quota-audit row, and an `ops_audit` row per action (`family.member_invite`, `family.member_invite_batch`, `family.limit_set`, `family.hold_set`, `family.member_revoke`). Batch audit metadata records **counts and row ids, never phone numbers**. | Same validation, same §19 floor, same push to the invitee. Phone lists in the audit trail would outlive a revoke (B-812 precedent).                                                                                            |
| D7  | **Batch add = a list of E.164 phones (≤200 per call), processed sequentially and independently, per-row outcome returned.** Outcomes: `ok`, `invalid_phone`, `duplicate_in_batch`, `not_a_bravo_user`, `not_an_individual_account`, `member_in_another_family`, `invite_already_pending`, `cannot_invite_self`.                                                                                                                                 | This is the "add them easier" the client asked for, inside the registered-only rule. Unregistered people come back as a list ops can chase. A CSV upload is the same endpoint behind a file picker — not built until asked.    |
| D8  | **The ops-added member still accepts in-app** (row is `pending` until accept).                                                                                                                                                                                                                                                                                                                                                                  | Consent stays with the person being linked; the `familyInvite` push already tells them.                                                                                                                                        |
| D9  | **The holder on the ops routes must be an `individual` account** (`resolveAccountKind`), else `holder_not_individual`.                                                                                                                                                                                                                                                                                                                          | The app path gets this for free (only individuals reach the screen); the ops path takes an arbitrary user id.                                                                                                                  |
| D10 | **Mobile list: keep the ScrollView; add a debounced search box + page-of-50 + "Show more" row.** No FlatList conversion.                                                                                                                                                                                                                                                                                                                        | Smallest diff on a 1,210-line screen with three pins on it (B-732 touch, sheet bottom pad, partial approval). A root with 2,000 members searches; nobody scrolls 40 pages. FlatList is the follow-up if device numbers say so. |
| D11 | **Push/activity copy goes neutral; push KINDS do not change.**                                                                                                                                                                                                                                                                                                                                                                                  | `serverWakeKindParity` pins the kind set producer↔consumer.                                                                                                                                                                    |

## 6. Edge cases (initial list — the edge-case agent extends this in §8)

1. Old APK at exactly 4 active members: sees the seat CTA, not Add — shim + ops nudge (D1). Verified by the compat test.
2. `q` containing `%`, `_`, `\`: escaped (B-636 lesson); a test pins the escape.
3. Batch with duplicates / the holder's own phone / an unregistered phone / a provider account / someone already in another root: each is its own row outcome, the rest of the batch proceeds.
4. Batch of 200 × ~5 queries: sequential, ~2–4 s; acceptable for a console action; the route is under `OPS_THROTTLE`.
5. Ops sets a limit below `spent_credits`: same `QUOTA_BELOW_SPENT` + minimum as the app (D6); the card renders it.
6. Ops removes a member mid-booking: identical to holder removal — ledger/audit stay, the open credit request is cancelled, the location fix is purged; a charge already in flight is settled by the B-384 charge-time re-resolve.
7. Ops invites for a holder who is NOT an individual account (provider/agent): `holder_not_individual` (D9).
8. Holder is themselves an active member of another root (one-level chain): unchanged existing behaviour — their own bookings bill their holder. Documented, not changed.
9. A root with 3,000 members opens the Pro sheet on a Redmi Note 11: first page 50 rows; header counts come from the server, not from `members.length`.
10. `usage()` top-50: a member outside the top 50 is still in `totalSpent` (SQL SUM) and still findable via search on the members list.
11. `IndividualProfileScreen` credit-request panel is unpaged (pending only) — bounded by the one-pending-per-member index; a root with 3,000 pending requests is a support problem, not a rendering one. Left as is.
12. The `family-invite` push to a member invited by ops reads "{holder} invited you" — same as the app path; nothing says "ops".
13. Search debounce + rapid typing + "Show more": each request carries the `q` it was issued with; a stale response for an older `q` is dropped (sequence guard) — pinned in the screen test.
